## 3. Hardware-independent ESP-NOW validation plan (Task 3)

"Hardware-independent" = the plan depends on nothing in the Android app: all
measurements come from firmware serial logs and the phone's nRF Connect screen,
recorded into `test-logs/results-template.csv` (§8). It can be executed the
moment boards arrive.

### 3.1 Metric definitions (what exactly gets measured)

| Metric | Definition | Logged by |
| :--- | :--- | :--- |
| Delivery % | `packets_acked / packets_sent × 100` over a full `send n gap` run | sender `--- STATS ---` |
| Ack match | every ACK's sequence number corresponds to an outstanding DAT; anomalies surface as `lateAck` and (manually cross-checked) `ack mismatches` | sender `[ACK] late/unexpected` lines |
| Duplicate handling | receiver counts a repeat sequence in `[DUP]` lines and still ACKs (idempotent); duplicates ≈ retransmissions by design | receiver `[DUP]` lines |
| Timeout/retransmit | per-attempt deadline 150 ms, up to 3 attempts; bounded resolution time per packet | sender `[TO ]` / `[LOST]` lines |
| RTT | `ACK time − final transmit time`, min/avg/max per run | sender STATS |
| BLE stability | connect/disconnect events with timestamps; MTU; effective connection interval as reported by the phone | board `[GATT]` lines + nRF Connect |
| Reconnect/recovery | time from peer/central loss to resumed traffic (targets in §7) | timestamps in logs |
| Range | delivery % + RSSI at fixed distances and environments | sender STATS + `[RX ] rssi=` |

### 3.2 Test matrix

| ID | Stage (MILESTONE-2.md §2) | Procedure | Key outputs |
| :--- | :--- | :--- | :--- |
| T0 | 1 — Firmware/boot | Compile both projects; flash both boards; boot banners show MAC + channel; observe ≥2 min without reboot | build logs, boot capture |
| T1 | 2 — Delivery | Board A: `send 1000 50` (boards 0.5–1 m apart); then `send 1000 50` from board B (reverse direction) | delivery %, RTT, RSSI |
| T2 | 2 — Acknowledgements | Same runs; cross-check STATS `acked+lost == sent`, `lateAck`, count of `[ACK] late/unexpected` lines | ack correctness |
| T3 | 2 — Duplicates | From T1 runs: receiver `dupDetected` vs sender `retrans` (each retransmitted DAT should yield exactly one `[DUP]`); also run `send 200 10` (10 ms gaps, tight timing) | dup detection rate |
| T4 | 2 — Timeouts/loss bound | Start `send 500 50`, power off board B mid-run; every seq after cutoff must resolve as `LOST` within `3 × 150 ms`, sender must not stall; power B back for T5 | bounded failure behavior |
| T5 | 3/5 — Reconnect & recovery | (a) ESP-NOW: power-cycle B → A prints `PEER LOST` ≤5 s, re-learns peer ≤1 s after B's reboot. (b) BLE: toggle phone Bluetooth / walk out of range → board re-advertises (auto), phone reconnects, re-subscribes notifications. (c) BLE disconnect during an active `send` run → ESP-NOW unaffected, BLE recovers | recovery timings |
| T6 | 4 — **Combined BLE + ESP-NOW** | Phone connected over NUS (nRF Connect) while board runs `send 1000 50`. Variants: **T6a** phone idle-connected; **T6b** phone actively scanning/refreshing services (worst-case radio contention); **T6c** after firmware's 100–200 ms connection-interval request — **verify the effective interval in nRF Connect, don't assume**. Compare delivery to T1 baseline | delivery delta vs baseline, BLE drops, effective conn interval |
| T7 | 5 — Range | `send 100 50` at 10 m / 25 m / 50 m / 100 m outdoors (open, semi-urban per PLAN.md) + indoor multi-room; note environment, body blocking, weather | delivery %, RSSI per distance |
| T8 | 5 — End-to-end offline | Both phones in Airplane Mode (Bluetooth + GPS on), no internet anywhere: phone A writes `TEST,123` to board A's NUS → ESP-NOW → board B notifies phone B. 50 messages | e2e delivery %, latency |

## 5. BLE + ESP-NOW compatibility on the proposed board (Task 5)

**Board: ESP32-C3** (single-core RISC-V, one 2.4 GHz radio, BLE 5 only — no
Bluetooth Classic).

### 5.1 Verified facts (primary sources)

| # | Fact | Source |
| :-- | :--- | :--- |
| V1 | ESP32-C3 has **one** 2.4 GHz RF module shared by Wi-Fi and BLE. A module cannot receive/transmit while another is transmitting; the chip arbitrates by **time-division multiplexing**. | [RF Coexistence — ESP32-C3, ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c3/api-guides/coexist.html) |
| V2 | Coexistence matrix: **ESP-NOW RX while BLE is scanning/advertising/connected = "S" — supported and stable *only in Wi-Fi STA mode*, otherwise not supported.** ESP-NOW TX = "Y" in all BLE states. SoftAP+BLE rows = "C1" (unstable). Our firmware therefore runs `WIFI_STA` and never associates with an AP. | same matrix |
| V3 | With Wi-Fi connected + BLE connected, the documented coexistence scheme splits the radio ~**50/50 time slices**; priorities are dynamic and BLE advertising events can preempt the Wi-Fi slice. **Some RX loss is expected even in the fully "supported" case.** | same guide |
| V4 | ESP-NOW requires Wi-Fi started; **all devices must share the same Wi-Fi channel**; a mismatched peer channel fails sends (`ESP_ERR_ESPNOW_CHAN`), and a STA associating to an AP on another channel can **silently** break ESP-NOW RX (open issue IDFGH-17728). | [ESP-NOW API](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html), [ESP-FAQ](https://docs.espressif.com/projects/esp-faq/en/latest/application-solution/esp-now.html) |
| V5 | Espressif states ESP-NOW delivery **is not guaranteed** and explicitly recommends application-layer **sequence numbers (dedup) + ACK + retransmit-on-timeout**. Our firmware implements exactly this — the reliability layer is required, not optional. | [ESP-NOW API](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html) |
| V6 | IDF 5.5 **breaking change**: ESP-NOW send callback's first parameter became `esp_now_send_info_t *`; IDF 5.0 changed the receive callback to `esp_now_recv_info_t *`. Toolchain pins in §6.2 choose which branch compiles. | [IDF 5.5 Wi-Fi migration](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/migration-guides/release-5.x/5.5/wifi.html), [IDF 5.0 networking migration](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/migration-guides/release-5.x/5.0/networking.html) |
| V7 | **Issue-tracker evidence (not the manual):** IDFGH-16797 (Nov 2025) reported ESP-NOW RX completely dead while BLE active on IDF 5.5.1; Espressif's maintainer could not fully reproduce, said `CONFIG_ESP_COEX_SW_COEXIST_ENABLE` must be selected, and noted an ESP-NOW-coexistence fix **between IDF 5.5.0 and 5.5.1**; the reporter still measured 98–100% loss after matching configs. Corroborating: [Stack Overflow](https://stackoverflow.com/questions/77766050/bluetooth-and-espnow-dont-work-together-esp32) (ESP-NOW RX stops when BLE scanning starts). | [esp-idf issue #17874](https://github.com/espressif/esp-idf/issues/17874) |
| V8 | BLE data hops across 37 channels spanning **2402–2480 MHz**, overlapping *every* 2.4 GHz Wi-Fi channel (1–13). Choosing Wi-Fi channel 1/6/11 dodges local Wi-Fi access points but **cannot dodge BLE** — coexistence contention is unavoidable by channel selection. | Bluetooth Core Spec (2.4 GHz ISM hopping) |
| V9 | Android permissions: API ≥31 (Android 12+) needs runtime `BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT`; API ≤30 needs `ACCESS_FINE_LOCATION` (location services ON for scans). `neverForLocation` can drop location but filters some beacons. | [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions), [react-native-ble-plx docs](https://dotintent.github.io/react-native-ble-plx/) |

### 5.2 Assumptions (plausible, NOT verified here)

| # | Assumption | Why it matters / how Monday falsifies it |
| :-- | :--- | :--- |
| A1 | The Arduino framework's prebuilt sdkconfig enables SW coexistence (`CONFIG_ESP_COEX_SW_COEXIST_ENABLE=y`) by default. | If off, V7's failure mode is likely ours. **Check step in §6.4.** |
| A2 | The "S" rating transfers to *NimBLE-Arduino + Arduino wrapper* on ESP32-C3 (the matrix is IDF-level; Arduino wraps the same components). | T6 measures it directly. |

### 5.3 Unresolved risk R1 — mitigation ladder (pre-agreed, staged)

Execute only as far as results force; each rung is a **test outcome to log**,
not a failure to hide:

1. **Baseline conditions** (already in firmware): Wi-Fi STA mode, fixed channel
   1, modem-sleep off, coexistence matrix constraints respected — re-verify with
   T1/T6a.
2. **Long BLE connection intervals** 100–200 ms (firmware requests them;
   confirm the phone actually accepted — nRF Connect shows the effective value).
3. **Confirm SW coex is enabled** in the build's sdkconfig (§6.4 grep step).
4. **Toolchain move:** already on IDF 5.5.5 (primary) which contains the
   5.5.0→5.5.1 ESP-NOW-coexistence fix; if tests were run on the fallback
   toolchain (IDF 4.4.7), switch to primary before drawing conclusions.
5. **Native ESP-IDF fallback** with explicit coex preference — PLAN.md §6
   "Deep Mitigation" already specifies this direction; note its cited option
   `CONFIG_ESP_COEX_ENABLE` is stale (current: `CONFIG_ESP_COEX_SW_COEXIST_ENABLE`
   plus `esp_coex_preference_set(ESP_COEX_PREFER_WIFI)`) — see R4, pending
   approval to correct PLAN.md.
6. **Decision gate:** if loss stays >15% after rungs 1–5 (PLAN.md's own
   escalation threshold), the *architecture* is what changes (scheduling BLE
   around ESP-NOW bursts, different module, or re-scoping V1 range) — not the
   firmware. Bring results, not guesses, to that conversation.

| 2 | Acknowledgements (T2) | `acked + lost == sent`; every ack matched a sent seq; lateAck explained by retrans only | lateAck > retrans (timeout too tight — retune) | acks for never-sent seqs / zero acks |
| 2 | Duplicates (T3) | dupDetected ≈ retrans (±2%); duplicate counted, receiver state not reprocessed | mismatch >2% | dups undetected or block retrans recovery |
